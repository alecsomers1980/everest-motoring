# OTP → RLV / NCO paperwork: design

**Date:** 2026-10-10
**Status:** approved in brainstorming, awaiting spec review

## Problem

For every used-car sale, Everest staff download the Offer to Purchase (OTP) from their dealer management system. They then copy the same customer and vehicle details by hand onto two NaTIS forms: the **RLV** (blue, application for registration and licensing) and the **NCO** (yellow, notification of change of ownership). The goal: upload the OTP once and download both forms pre-filled.

Rule from the client: **any box we are not sure of stays blank.**

## Source documents

- **OTP:** "CONTRACT FOR THE SALE OF A USED MOTOR VEHICLE", 6 pages, generated by ActiveReports 13 (the dealer system). It is a text PDF with a fixed layout, and all deal data is on page 1 as label/value pairs on fixed rows. The customer's **SA ID number is printed in the "VAT No." box**.
- **RLV:** `RLV(5)(2012/03)`, 4 pages, A4.
- **NCO:** `NCO(6)(2012/03)`, 3 pages, A4.
- Neither RLV nor NCO has fillable form fields. Both are vector PDFs (Acrobat Distiller), so every character box is a drawn rectangle whose coordinates can be extracted.

The OTP does not say how the car is financed (its boilerplate says "paid in cash"). Staff pick the finance option on upload.

## Decisions

| Question | Decision |
|---|---|
| Financed deal routing | Bank = title holder. Financed: RLV Part A = bank, RLV Part B = customer, NCO Part B = bank. Cash: RLV Part A = customer, RLV Part B blank, NCO Part B = customer. NCO Part A is always Everest. |
| Storage | Produce and forget. No deal or customer data is stored. Re-download = re-upload the OTP. |
| Derived values | Fill clear derivations (gender/DOB from a valid SA ID, transmission and body type from the model name, colour, reasons). Highlight them on the review screen. |
| Sale date | Order date → NCO "date of change" and RLV "date liable for registration". |
| Architecture | Everything runs in the browser: `unpdf` reads the OTP, `pdf-lib` fills the forms. The server only serves the finance-house list. |

Rejected: a server route (customer PII would transit Vercel for no gain), and Claude/LLM extraction (per-upload cost, and it can invent values, which conflicts with the blank-if-unsure rule).

## User flow

New admin page **Stock → Paperwork** at `/admin/paperwork` (admin role only, inherited from `src/app/admin/layout.js`).

1. **Upload:** pick the OTP PDF, and choose **Cash** or a finance house from a dropdown.
2. **Review:** one screen grouped into Customer / Vehicle / Sale. Every value the system can fill is shown and editable, tagged with its origin:
   - **From OTP:** copied verbatim.
   - **Derived:** highlighted, with a short source note (e.g. "from ID number", "from model name").
   - **Blank:** shown as "not on OTP". Staff may type a value or leave it for the pen.
   - **Edited:** changed by staff on this screen.

   A value longer than its row of boxes shows a warning with the box count, so staff can shorten it. Boxes the system never fills (vehicle category, fuel, kW/cc, tare/GVM, NaTIS model no., steering, use, sector, nature of ownership, public road, signatures and dates) are listed in a "fill in by hand" note. The fixed marks (title-holder transaction, self-propelled, reason "ownership", reason "sold") and the NCO seller details are listed as "always on the forms".
3. **Download:** two buttons, **RLV (blue)** and **NCO (yellow)**. Each produces the original blank form with the reviewed values stamped in block capitals, one character per box, and X marks in tick boxes. Nothing is persisted.

**Finance houses** tab on the same page: list, add, edit and delete banks.

The layout maps are generated once by measuring the box rectangles in the blank PDFs. They are committed as data and not recomputed at runtime.

## Reading the OTP

All fields come from page 1. A field's value is the text to the right of its label on the same row (within a y-tolerance), up to the next label column. A missing label or an empty value gives a **blank**. No fallback guessing.

- **Reject** if page 1 lacks "CONTRACT FOR THE SALE OF A USED MOTOR VEHICLE" or "DEAL ID": "This isn't an OTP from the dealer system."
- **Reject** if page 1 has no text at all: "Upload the original PDF from the dealer system, not a scan or photo."

### Customer

| Form value | OTP source | Rule | Origin |
|---|---|---|---|
| Title, first names, initials, surname | First line of the Customer block | Leading title (Mr/Mrs/Ms/Miss/Dr/Prof/Mnr/Mev/Me/Mej) dropped. Surname = last word plus any directly preceding particles (van, der, den, de, du, le, la, von, ter; any capitalisation), always leaving at least one first name. First names max 3; initials = their first letters. | OTP |
| Organisation name | Same line, when there is no leading title or it contains Pty/Ltd/Limited/CC/Inc/Trust | Whole line is the organisation name; person-only boxes (initials, first names, gender, DOB) blank, and the "VAT No." value is not read as an ID | OTP |
| ID number | "VAT No." value | Only if 13 digits and a valid SA ID (Luhn checksum + real date). Otherwise blank. | OTP |
| ID type | ID number | RSA ID when the ID number is valid; otherwise blank. Editable (RSA ID / foreign ID / traffic register / business reg.). | Derived |
| Gender | ID number | Digits 7–10: 0000–4999 female, 5000–9999 male. Only with a valid ID. | Derived |
| Date of birth | ID number | YYMMDD. Century = 20xx if that is not in the future relative to the order date, else 19xx. Only with a valid ID. | Derived |
| Street address lines, city, postal code | Customer block lines between name and the next label | Last line matched as `CITY [PROVINCE] NNNN` (province ∈ GP, MP, KZN, WC, EC, NC, NW, FS, LP; optional). The lines above it are the street address, with a trailing comma trimmed. If the last line doesn't match, the street lines are kept and city/code are blank. | OTP |
| Suburb, postal address, notices address | n/a | Not on OTP | Blank |
| Email | "Email:" | Verbatim | OTP |
| Cellphone | "Mobile:" | Digits only | OTP |
| NCO day contact number (code / number) | "Mobile:" | Split as first 3 digits / rest when it is a 10-digit number starting with 0 | Derived |
| RLV home, day-contact and fax numbers | n/a | Not on OTP (the RLV has its own cellphone box) | Blank |

### Routing

| Form part | Cash | Financed |
|---|---|---|
| RLV A (title holder) | Customer | Finance house |
| RLV B (owner) | Blank | Customer |
| NCO A (seller) | Everest | Everest |
| NCO B (buyer) | Customer | Finance house |
| RLV C / NCO C (vehicle) | Vehicle | Vehicle |

**Everest constants (NCO A):** name DECAR BELEGGINGS (PTY) LTD; ID type business reg. no.; 2011/007142/07; day phone 013 / 8540600. Everest's email and NaTIS proxy are unknown and stay blank until supplied.

## Finance houses

`finance_houses` columns (all text except id and timestamps; all optional except `name`):

- `id`, `name` (display + form name), `id_type` (`business_reg` | `traffic_register`), `id_number`, `nature` (`private_company` | `close_corporation` | `other`), `nature_other`
- `email`, `phone_code`, `phone_number`, `fax_code`, `fax_number`
- `postal_line1..3`, `postal_suburb`, `postal_city`, `postal_code`
- `street_line1..3`, `street_suburb`, `street_city`, `street_code`
- `notices_to` (`postal` | `street`)
- `proxy_id_type` (`traffic_register` | `rsa_id` | `foreign_id`), `proxy_id_number`, `proxy_surname`, `proxy_initials`
- `created_at`, `updated_at`

The table starts empty. Staff add their banks (WesBank etc.) with the real figures. No values are seeded, because we would be guessing registration numbers.

## Filling the forms

- ID numbers (customer, bank, proxy, Everest's 2011/007142/07) are printed without slashes or spaces, because the form gives 13 single-character boxes.
- Only the proxy blocks with a data source are mapped: RLV Part A proxy and NCO Part B proxy (a bank's proxy). The customer's and Everest's proxy blocks stay blank.
- Every character is uppercased and drawn centred in its box in Helvetica Bold. A string longer than its box run is drawn shrunk to fit across the run rather than truncated, and the review screen has already warned about it.
- Tick boxes get a centred "X".
- Dates go into the `2:0YY : MM : DD` box groups.
- An empty value draws nothing.

## Errors

- Wrong document or scan: rejected with the messages above, and nothing else happens.
- The finance houses table is missing (migration not yet run): the dropdown offers Cash only, with a note that finance houses aren't set up yet. Upload, review and download still work.
- PDF generation failure: an inline error and no download. Reviewed values stay on screen.

## Testing

The repo is **public**, so the real OTP (customer ID number, address, email) is **never committed**. Tests use a synthetic fixture: the page-1 text-item layout of a real OTP with every value replaced by fake data.

- `saId`: valid/invalid checksums, impossible dates, gender boundary 4999/5000, century rule.
- `parseOtp`: fixture → expected Deal; invalid ID → ID/gender/DOB blank; "van der Merwe" surname; organisation customer; missing labels → blank; non-OTP text → rejected; empty text → scan rejection.
- `buildForms`: cash and financed routing per the table above; blanks stay blank.
- `fillForm`: fill a template, read the text back with `unpdf`, and check each value lands inside its box rectangle.

## Success criteria (checked in a separate pass after the build)

1. The real sample OTP (local only, never committed) produces an RLV and NCO where every filled box matches the OTP and the rules above. This is verified by rendering the filled pages to images and inspecting them.
2. Every value marked Blank above is absent from the filled PDFs.
3. Cash and financed (with a test finance house) route parties exactly as in the routing table.
4. Finance-house add, edit and delete works in a real browser. A non-admin is redirected away from `/admin/paperwork`, and the finance-house server actions refuse non-admins.
5. Driving the upload → review → download flow sends no network request carrying the OTP or customer data.
6. `npm test` passes and `next build` is clean (run with no dev server active).

## Out of scope

- An NCO for a trade-in (customer selling to Everest), even though the OTP has a "Less Trade(s)" section
- OTPs from other dealer systems
- Saving deals or linking to `sales` records
- Everest's NaTIS proxy details (blank until the client supplies them)
